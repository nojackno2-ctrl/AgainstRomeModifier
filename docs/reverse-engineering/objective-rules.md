# Objective rules: lowering to the verified ScenarioEvent path

2026-10-08, Codex, Task C. Isolated worktree `ARM_wt_objectives`, branch
`wt/objectives`, base `080ebc9`. No installed-game access or game launch.

## Output contract and corrected assumptions

At this revision BciObjectiveCompiler already returned ScenarioEvents, rather
than a separate raw byte layout. However, those events silently ignored graph
prerequisites, attached Victory to the last primary regardless of other goals,
truncated target/custom lists, ignored timeouts, and interpreted area hold time
as a deadline from level start (sometimes without any target condition).
Generated Chinese messages also violated the existing strict CP1251 validator.

The replacement has **no independent BCI encoder**. `Compile` lowers supported
rules to ScenarioEvent/ScenarioCondition/ScenarioAction and invokes
ScenarioEventValidator. `CompileToBci` accepts a pristine raw BCI0 or PFIL
original and current ScenarioDocument, preserves existing events, uses
LevelScriptInjector.Inject for script placements and ScenarioEventCompiler.Inject
for polling, then checks BciImage serialization round trip. It returns bytes
in the same wrapper format without writing files or changing its inputs.
Use the original backup on every compilation, not an already injected script.
To save, add the returned CompiledEvents to the scenario once and use the
existing transactional LevelScriptInjector.Apply path; its backup makes
repeated saves byte-identical. No Objectives UI/save integration was added.

Exactly one primary, no graph edges, and initially Active objectives are
required. All diagnostics with Error suppress **all** generated events/bytes.
Compile without a scenario validates structure only and explicitly reports
OBJ_BINDING_UNCHECKED. CompileToBci requires current target bindings. Reward
SpawnUnit aliases must be supplied from the actual alias catalog; they are
never inferred from the reward itself. Text must be representable in CP1251.
Autogenerated notices are English; titles/reward text are validated unchanged.

## Supported compositions

| Rule | Existing event primitives | Scope |
|---|---|---|
| AssassinateTarget / DestroyBuilding | ObjectDeadOrRemoved for every explicit target, AND; Message/reward; Primary ends in Victory | 1-32 distinct targets; all must qualify in one poll, no truncation; Primary or Bonus |
| Survival | DelaySeconds = duration from level start; ObjectExists; companion ObjectDeadOrRemoved -> Defeat first | One target, Primary; no activation-relative timer; target must still exist at/after deadline |
| Protected asset FailureCriterion | ObjectDeadOrRemoved -> Message, Defeat | Survival kind, one target, no duration/reward |
| EscortUnit | ObjectInArea -> Message/reward, Victory; ObjectDeadOrRemoved -> Defeat first | One target, rectangular destination, Primary |
| CaptureArea (zero hold only) | ObjectInArea -> Message/reward; Primary ends in Victory | Explicit one-target location check, not team ownership or enemy clearance |
| CustomScripted | 1-32 existing ScenarioConditions combined with AND | No empty condition set; Primary or Bonus; no custom data/timer |

Objective failure events precede all objective completions, regardless of graph
insertion order. The existing ARM_MISSION_ENDED guard prevents later generated
events from overwriting Defeat with Victory in the same or future polls. Bonus
completions precede the primary terminal event. Pre-existing scenario events
retain their order and run before the generated block; a pre-existing terminal
event can end the mission before any objective event.

These are compositions of existing primitives, **not new gameplay verification**.
ObjectExists includes corpses. A protected/escort corpse therefore must be
handled by its earlier loss event. ObjectDeadOrRemoved only detects removal
following a successful observed existence, so a target removed before the first
poll (or never successfully spawned) does not qualify. A never-spawned survival
target cannot win while missing; if it first appears after the deadline, it can
qualify then. This is not a guarantee of uninterrupted alive presence throughout
the countdown. Script unit targets refer to the troop container, not individual
members. Multi-target destruction is a simultaneous AND of current primitives,
not independently latched kill-count progress. Custom/capture location checks
can qualify for a corpse whose position remains valid, as the primitive does.

## Explicitly unsupported export features

- EliminateAllEnemies: explicit partial targets do not establish team-wide loss.
- KingOfTheHill, positive CaptureArea hold, any cumulative/continuous dwell timer.
  Scenario DelaySeconds is a minimum deadline, not duration in the area.
- Prerequisite, CompositeAnd, CompositeOr, MutuallyExclusive; multiple primaries;
  Hidden/Inactive/Completed/Failed/Abandoned initial states. No exposed event
  completion/state primitive establishes faithful graph progression.
- Circle areas (no bounding-box approximation), time limits, RequiredCount other
  than 1, resource goals, kill counts, CustomData and unused extra conditions/areas.
  Resource and kill rules have no dedicated kind in this source revision.
- Bonus survival/escort: failing a bonus must suppress its later completion;
  no exposed per-objective failure latch does that.
- Reward terminal actions, unknown primitives/aliases, invalid/unbound targets,
  lists/events/actions exceeding existing limits (32/256/32).

ObjectiveRuleCatalog.Validate remains design/model validation for graph editing;
ValidateForCompilation is the stricter export gate. AllDescriptors includes
simulation-only designs. ObjectiveSandboxSession.ExportDiagnostics exposes that
gate independently of sandbox outcome. The sandbox is a conceptual offline
state machine, not a BCI VM; its victories and dependency progression are not
export or game evidence. The old dependency compiler test was changed to expect
rejection because its previous success assertion validated ignored prerequisites.
Existing graph/serialization/sandbox tests remain, including offline dwell tests.
The CaptureArea factory defaults to zero hold and accepts an optional explicit
targetGuid; omitted targets remain nonexportable.

## Reproducible verification and limits

Unit tests compile every supported kind, invoke ScenarioEventValidator, emit
with the existing compiler and parse/serialize BciImage. Reused ScenarioEvents
TestVm executes the actual serialized bytecode: countdown/loss priority,
corpse-in-destination loss, all-target destruction, preservation of existing
events and simultaneous failure/primary completion. Regression tests reject
unsupported graphs/params, truncation, invalid conditions/rewards/encoding,
unbound targets, malformed originals and combined event limits.

TEMP opt-in tests use ARM_OBJECTIVE_SOURCE pointing to the source above. They
compile both original scripts in memory, compare source bytes afterward, and
compare CompileToBci output byte-for-byte with transactional Apply and repeated
Apply on fresh test directories. ARM_OBJECTIVE_DUMP can retain outputs only
under this worktree's TEMP directory. Proprietary assets are never committed.

$env:DOTNET_ROLL_FORWARD = 'Major'
$env:ARM_GAME_PATH = $null

$env:ARM_OBJECTIVE_SOURCE = Join-Path $env:TEMP 'ArmGameCompare_20261007'
